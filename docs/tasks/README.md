# Регламент выполнения задач

Роли: **стратег** (сессия планирования) пишет брифы и принимает работу; **исполнитель** (отдельная сессия, Opus 5.5)
делает одну задачу по одному брифу; **пользователь** запускает сессии, вливает ветки и отправляет на GitHub.

## Как запустить исполнителя

Новая сессия в этой же папке, модель Opus 5.5, сообщение:

> Выполни задачу T-12 по брифу docs/tasks/T-12-invites.md. Следуй CLAUDE.md и docs/tasks/README.md.

Перед запуском предыдущая задача должна быть влита в `main`.

## Порядок работы исполнителя

1. **Прочитай:** `CLAUDE.md`, этот файл, бриф. Из TZ.md и ARCHITECTURE.md — только разделы, на которые ссылается бриф.
   Затем код, который бриф называет образцом. Образец всегда есть: модуль `platform` (API + тесты) и страница
   `apps/web/src/pages/platform` (веб) сделаны по всем правилам проекта — повторяй их устройство.
2. **Ветка** `feat/t-NN-кратко` от свежего `main`. Если `main` не содержит предыдущую задачу — остановись и скажи.
3. **Делай слоями, проверяя каждый:**
   контракты в `shared` → схема и миграция → сервис и контроллер → e2e-тесты → веб или Mini App → проверка в браузере.
   Не пиши весь код сразу: после каждого слоя — типы и тесты этого слоя.
4. **Проверь всё** по списку «Готово, когда» из брифа и по общему списку ниже.
5. **Обнови** `IMPLEMENTATION_PLAN.md` (статус ✅, что сделано, что перенесено) и статус в таблице выше.
6. **Один коммит** в ветку. Не вливай в `main` и не отправляй на GitHub.
7. **Отчёт** пользователю по шаблону ниже.

## Общий список «готово» (для каждой задачи)

- [ ] Все пункты «Готово, когда» из брифа выполнены, либо в отчёте прямо сказано, какой не выполнен и почему.
- [ ] Типы без ошибок во всех затронутых пакетах; линтер и `prettier --check .` чистые.
- [ ] Все тесты API зелёные (полный прогон, а не только новые файлы).
- [ ] Новые эндпоинты школы добавлены в `describeSchoolIsolation`; для каждой роли из матрицы прав (TZ §7.3) есть тест
      «можно» или «нельзя».
- [ ] Миграция применена к базе разработки и к тестовой; старые миграции не тронуты.
- [ ] Экраны открыты в браузере и пройдены руками: основной сценарий, ошибка валидации, пустое состояние.
      Консоль браузера без ошибок. Вид сверен с прототипом там, где бриф называет образец.
- [ ] Нет строк интерфейса в коде, нет `any`, нет закомментированного кода, нет `console.log`.
- [ ] `.env` не тронут; новые переменные есть в `.env.example` и `env.ts`.
- [ ] В коде нет `TODO` без номера задачи: только `TODO(T-NN): что именно`.

## Когда остановиться и спросить

Останавливайся и пиши пользователю (а не решай сам), если:

- бриф противоречит коду или ТЗ, и от выбора зависит модель данных или контракт API;
- нужно удалить или переименовать столбец с данными, либо поменять уже применённую миграцию;
- нужно то, что запрещено в CLAUDE.md (секреты, `migrate reset`, push, чужие процессы);
- задача явно выходит за бриф: хочется переделать соседний модуль, поменять общий компонент или добавить библиотеку,
  которой нет в брифе;
- одна и та же команда упала больше трёх раз подряд с разными ошибками.

Мелочи (название переменной, порядок полей, текст подписи) решай сам и не спрашивай.

## Чего не делать

- Не расширяй задачу. Всё, что в брифе стоит в разделе «Не входит», остаётся несделанным, даже если «заодно удобно».
- Не подменяй проверку: нельзя ослаблять или пропускать тест, чтобы он прошёл. Тест упал — чини код или сообщи.
- Не выдумывай результат проверки. Не смог открыть экран или прогнать тесты — так и напиши.
- Не трогай данные пользователя в базе разработки, кроме создания тестовых записей через интерфейс; перечисли их в отчёте.

## Шаблон отчёта

```
T-NN готова / готова частично / остановлена.
Ветка: feat/t-NN-…, коммит <хэш>.

Сделано: 3–6 пунктов простыми словами.
Проверка: тесты X из Y; линтер, типы; что пройдено в браузере.
Не сделано или не проверено: по пунктам, с причиной. Если всё сделано — «нет».
Отступления от брифа: что и почему. Если нет — «нет».
Изменения вне кода: миграции, тестовые записи в базе, новые переменные окружения, запущенные серверы.
```

## Приёмка

После отчёта пользователь возвращается в сессию стратега: «проверь T-NN». Стратег читает дифф ветки, сверяет с брифом,
при необходимости прогоняет тесты и либо принимает, либо пишет список правок для исполнителя. Вливает ветку пользователь.

# T-19. Доменные правила списания

**Цель.** Правила «с какого абонемента и когда списывается занятие» и «как заморозка сдвигает срок» записаны чистыми
функциями в `packages/shared/src/domain` и покрыты таблицей тестов. Задачи T-20…T-24 только вызывают эти функции
и не решают заново, что списывать.

**Требования:** FR-26, FR-28 (расчёт), FR-29 и FR-30 (только формула остатка), FR-32 (исправление отметки — расчёт).

Задача без базы, API и экранов: только `packages/shared`. Ошибка здесь стоит денег родителям и школе, поэтому
каждое решение ниже закреплено строкой в таблице кейсов, а покрытие веток — 100%.

## Решения (уже приняты)

Согласовано с пользователем (влияет на модель данных T-20…T-22):

1. **Состояние оплаты отметки — два поля, как в ТЗ:** `charged` и `subscriptionId`. `charged` значит «занятие
   подлежит списанию», а не «списано из абонемента»:

   | `charged` | `subscriptionId` | Смысл |
   |---|---|---|
   | `false` | `null` | Не списывается (правило школы для пропуска или уважительной причины) |
   | `true` | задан | Оплачено абонементом (у помесячного остаток при этом не меняется) |
   | `true` | `null` | **Неоплаченное посещение** — попадает в отчёт должников |

   Сочетания `false` + абонемент не бывает.
2. **Абонемент подбирается по дате занятия, а не по сегодняшнему дню и не по статусу.** Если отметку ставят задним
   числом, а абонемент, действовавший в день занятия, уже «истёк» — занятие всё равно списывается с него, пока в нём
   есть остаток. Поэтому «сгорело N занятий» — не снимок, а `lessonsTotal − lessonsUsed` истёкшего абонемента
   (T-21 пересчитывает `burned_lessons` после каждого списания и возврата). Не подходит только `cancelled`.
3. **Заморозок у абонемента может быть несколько**, в том числе назначенных на будущее; они не пересекаются.
   «Заморожен ли на дату» вычисляется по строкам `SubscriptionFreeze`. Статус `frozen` в таблице — лишь признак
   «заморожен сегодня» для списков; функции домена на него не смотрят.
4. **Остаток = `lessonsTotal − lessonsUsed`.** Ручная корректировка (FR-30) меняет `lessonsTotal`;
   `lessonsUsed` меняют только списания и возвраты по отметкам.

Решения стратега:

5. **Какие статусы списывают.** `present` — всегда. `absent` — если `chargeAbsent` (по умолчанию да). `excused` —
   если `chargeExcused` (по умолчанию нет). Отменённое занятие и снятая отметка не списывают ничего (UC-9).
6. **Какой абонемент подходит** (все условия сразу): тот же курс; статус не `cancelled`;
   `startsOn ≤ дата занятия ≤ endsOn` (обе границы включительно); дата не попадает ни в одну заморозку;
   у `monthly` остаток не проверяется, у `lessons` и `single` остаток > 0.
7. **Какой выбирается из нескольких подходящих:** с ближайшим `endsOn` (FR-26) — вид абонемента не важен, помесячный
   и по занятиям соревнуются только датой. При равном `endsOn` — с более ранним `startsOn`; при равных обоих —
   с меньшим `id` (UUID v7, то есть созданный раньше). Результат не зависит от порядка во входном массиве.
8. **Абонементы не комбинируются и не уходят в минус.** Если ближайший исчерпан, он просто не подходит (п. 6) и
   берётся следующий; если не подходит ни один — неоплаченное посещение.
9. **Помесячный абонемент:** отметка получает его `subscriptionId`, но `lessonsUsed` не меняется — операций
   списания и возврата для него нет. Статистика посещений считается по отметкам. `single` (разовое, пробное) ведёт
   себя как `lessons` с `lessonsTotal = 1`.
10. **Исправление отметки не перевыбирает источник оплаты без нужды:**
    - статус не изменился (повторное сохранение) — не меняется ничего, даже если школа с тех пор поменяла правило
      или у ученика появился новый абонемент. Преподаватель сохраняет всю группу целиком, и повторное сохранение
      не должно двигать деньги;
    - было «не списывается» → стало «списывается»: абонемент подбирается, как для новой отметки;
    - было «списывается» → стало «не списывается» (или отметка снята): занятие возвращается в тот же абонемент,
      даже если он уже истёк или отменён; неоплаченное посещение просто перестаёт быть долгом;
    - было «списывается» → осталось «списывается» (например, «был» → «пропуск» при `chargeAbsent`): источник
      прежний. Оплаченное остаётся на том же абонементе; **неоплаченное остаётся неоплаченным**, даже если абонемент
      уже появился — погашение идёт только через подтверждение админа (FR-27, T-24).
    - Правило школы берётся текущее, на момент исправления; старые отметки при смене правила не пересчитываются.
11. **Дата занятия** — календарная дата его фактического начала (`Lesson.startsAt`, для перенесённого — новое
    время) **в часовом поясе школы**: `utcToZoned(startsAt, school.timezone).date`. Функции списания принимают
    готовую `DateString` и про пояса не знают; переводит вызывающий сервис. Занятие в 23:59 последнего дня
    абонемента по времени школы списывается; в 00:00 следующего дня — уже нет.
12. **Заморозка.** `from` и `to` — даты в поясе школы, обе включительно; длина = `daysBetween(from, to) + 1`.
    `endsOn` сдвигается ровно на длину, у абонементов всех видов (у помесячного «календарный месяц» после заморозки
    заканчивается не в последний день месяца — это нормально). Хранимый `endsOn` уже включает все заморозки,
    заново их никто не прибавляет. Заморозка может выходить за текущий `endsOn`.
13. **Когда заморозка недопустима** (проверки в таком порядке, возвращается первая сработавшая):
    абонемент `cancelled` → `SUBSCRIPTION_CANCELLED`; `to < from` → `FREEZE_RANGE_INVALID`; длина больше 365 дней →
    `FREEZE_TOO_LONG`; `from < startsOn` или `from > endsOn` → `FREEZE_OUTSIDE_SUBSCRIPTION`; пересекается
    с существующей заморозкой (общий день — уже пересечение) → `FREEZE_OVERLAP`.
    Проверку «в периоде уже есть списанные с этого абонемента отметки» делает сервис T-21 — ей нужны данные базы.
14. **Досрочное снятие** в день `today` (сегодня в поясе школы): сегодня абонемент уже снова действует, последний
    замороженный день — вчера. Если `today ≤ from` — заморозка удаляется целиком; если `from < today ≤ to` — её
    `to` становится `today − 1`; `endsOn` уменьшается на число снятых дней. Если `today > to` — заморозка уже
    закончилась, снимать нечего.

## Домен: `packages/shared/src/domain`

Чистые функции: без базы, без текущего времени (`today` приходит параметром), входные объекты не изменяются.
Экспорт из `index.ts`. Типы статусов и видов объяви здесь же константами (`ATTENDANCE_STATUSES`,
`SUBSCRIPTION_KINDS`, `SUBSCRIPTION_STATUSES` — `as const` + тип, как `LESSON_STATUSES` в `contracts/lessons.ts`);
контракты T-20 и T-22 возьмут их отсюда.

**`subscriptions.ts`**

```ts
type SubscriptionKind = 'lessons' | 'monthly' | 'single';
type SubscriptionStatus = 'active' | 'frozen' | 'expired' | 'cancelled';
interface FreezePeriod { from: DateString; to: DateString }          // both inclusive
interface SubscriptionState {
  id: string; courseId: string; kind: SubscriptionKind; status: SubscriptionStatus;
  lessonsTotal: number | null;                                       // null for monthly
  lessonsUsed: number;
  startsOn: DateString; endsOn: DateString;                          // endsOn already includes every freeze
  freezes: FreezePeriod[];
}
type FreezeProblem = 'SUBSCRIPTION_CANCELLED' | 'FREEZE_RANGE_INVALID' | 'FREEZE_TOO_LONG'
                   | 'FREEZE_OUTSIDE_SUBSCRIPTION' | 'FREEZE_OVERLAP';
```

- `remainingLessons(sub): number | null` — `null` для `monthly`, иначе `lessonsTotal − lessonsUsed`.
- `isFrozenOn(sub, date): boolean` — п. 12.
- `freezeProblem(sub, from, to): FreezeProblem | null` — п. 13.
- `freezeShift(sub, from, to): DateString` — новый `endsOn` (п. 12). Допустимость не проверяет: сервис сначала
  вызывает `freezeProblem`.
- `unfreezeShift(sub, freeze, today): { endsOn: DateString; freeze: FreezePeriod | null } | null` — п. 14:
  `freeze: null` — заморозку удалить; результат `null` — снимать нечего.

**`charging.ts`**

```ts
type AttendanceStatus = 'present' | 'absent' | 'excused';
interface ChargePolicy { chargeAbsent: boolean; chargeExcused: boolean }
interface AttendanceCharge { status: AttendanceStatus; charged: boolean; subscriptionId: string | null }
type ChargeOperation = { type: 'refund' | 'charge'; subscriptionId: string };   // lessonsUsed −1 / +1
interface AttendanceChange { charged: boolean; subscriptionId: string | null; operations: ChargeOperation[] }
```

- `shouldCharge(status, policy): boolean` — п. 5.
- `pickSubscription(subs, courseId, lessonDate): SubscriptionState | null` — п. 6–8.
- `applyAttendanceChange({ prev, nextStatus, policy, subscriptions, courseId, lessonDate }): AttendanceChange` —
  п. 9–10. `prev: AttendanceCharge | null` (`null` — отметки не было), `nextStatus: AttendanceStatus | null`
  (`null` — отметка снята или занятие отменено). `subscriptions` — **все** абонементы ученика, включая истёкшие и
  отменённые: по ним ищется прежний абонемент для возврата. Возвращает новое состояние отметки и операции над
  `lessonsUsed`; операций не больше двух, возврат идёт раньше списания. Для помесячного абонемента операций нет.
  Если `prev.subscriptionId` нет в `subscriptions` — `throw new Error(...)`: это ошибка вызывающего кода, молча
  терять возврат нельзя.

Сервис T-22 вызывает `applyAttendanceChange` внутри транзакции с `SELECT … FOR UPDATE` на абонементы ученика и
для учеников одной группы — по очереди, перечитывая остаток; в самой функции про это ничего нет.

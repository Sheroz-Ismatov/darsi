# T-16. Расписание и генерация занятий

**Цель.** Админ задаёт группе правила расписания (дни недели, время, длительность), система сама создаёт занятия
на 8 недель вперёд, каждый день продлевает горизонт и предупреждает о накладках у преподавателя.

**Требования:** FR-13, FR-14.

Это первая задача, где ошибка стоит дорого: неверное время занятия увидят все родители. Поэтому расчёт вынесен
в чистые функции с полным покрытием тестами, а сервис только читает и пишет базу.

## Решения (уже приняты)

1. **Работа с часовыми поясами — свой код на `Intl`, без библиотек.** Таджикистан и Россия не переводят часы,
   но функции должны быть верны и для зон с переводом (проверяется тестом на `Europe/Berlin`).
2. **Занятия не пересоздаются без нужды.** При изменении правил сравниваем «что должно быть» и «что есть»:
   лишние будущие занятия удаляем, недостающие создаём, совпавшие не трогаем (их id сохраняются).
3. **Какие занятия система вправе удалить:** созданные по правилу (`scheduleRuleId` задан), со статусом `planned`,
   в будущем, не перенесённые (`originalStartsAt` пуст) и без отметок посещения. Отметок пока нет — в описании
   занятия есть поле `hasAttendance`, сервис передаёт `false` с пометкой `TODO(T-22)`.
4. **Занятый слот не заполняется заново.** Слот занят, если на это время есть любое занятие группы (в том числе
   отменённое) или занятие, перенесённое *с* этого времени (`originalStartsAt`).
5. **Правила не удаляются, если по ним были занятия:** им ставится `validTo` = вчера. Правило без единого занятия
   удаляется. Совпадающие правила (день, время, длительность) остаются теми же строками.
6. **Ежедневное продление — `@nestjs/schedule` внутри процесса API**, а не очередь BullMQ. Очереди появятся в T-38,
   тогда задача переедет. Запуск включается переменной `JOBS_ENABLED` (по умолчанию `true`, в тестах `false`).
   Блокировок не нужно: API один, а повторный запуск безопасен благодаря уникальному индексу.
7. **Накладки не мешают сохранению** — это предупреждение (FR-14).
8. **Время в запросах — местное время школы** (`'HH:mm'`), в ответах — момент в UTC (ISO). Панель показывает время
   в часовом поясе школы из `useSchool()`, а не в поясе браузера.

## Домен: `packages/shared/src/domain`

Чистые функции, без обращения к базе и к текущему времени (оно приходит параметром). Экспорт из `index.ts`.

**`time.ts`**
- `zonedDateTimeToUtc(date: 'YYYY-MM-DD', time: 'HH:mm', timeZone): Date` — если такого местного времени нет
  (перевод часов вперёд), берётся ближайшее следующее; если оно бывает дважды — первое.
- `utcToZoned(instant: Date, timeZone): { date: 'YYYY-MM-DD', time: 'HH:mm', weekday: 1..7 }` (1 — понедельник).
- `addDays(date: 'YYYY-MM-DD', days): 'YYYY-MM-DD'`, `todayIn(timeZone, now: Date): 'YYYY-MM-DD'`.

**`schedule.ts`**
- `planLessons({ rules, from, to, timeZone, groupStartsOn, groupEndsOn })` → `[{ ruleId, startsAt, durationMin }]`:
  все занятия по правилам за даты `from…to` включительно, с учётом `validFrom`/`validTo` правила и дат группы.
- `diffLessons({ planned, existing, now })` → `{ toCreate, toDeleteIds }` по решениям 2–4.
  `existing`: `{ id, startsAt, originalStartsAt, status, scheduleRuleId, hasAttendance }`.
- `findConflicts(mine, others)` → пары пересекающихся по времени занятий (касание границами — не пересечение).

**Тесты домена.** В `packages/shared` добавь Vitest (та же версия, что в `apps/api`) и `@vitest/coverage-v8`, скрипт
`test`. Покрытие веток файлов `domain/*` — 100% (порог в конфигурации, чтобы CI падал при снижении). Обязательные случаи:
- `Asia/Dushanbe` (+5): занятие в понедельник 09:00 → 04:00 UTC; занятие в 02:00 местного приходится на предыдущие
  сутки UTC и остаётся понедельником местного времени;
- `Europe/Moscow` (+3) — те же проверки;
- `Europe/Berlin`: недели перевода часов весной и осенью — местное время занятия не «уезжает»;
- границы: `from`/`to` включительно; `validTo`; `groupEndsOn`; правило на день, которого нет в диапазоне;
- `diffLessons`: ничего не изменилось → пустой результат; сменили время → старые удалены, новые созданы;
  отменённое занятие держит слот; перенесённое держит исходный слот и само не удаляется; прошедшие не трогаются;
  занятие с отметкой не удаляется; разовое (`scheduleRuleId` пуст) не удаляется.

## Данные

```
enum LessonStatus { planned done cancelled }

ScheduleRule: id, schoolId, groupId, weekday (1–7), startTime ('HH:mm'), durationMin,
              validFrom (date), validTo? (date), createdAt          @@index([groupId])
Lesson: id, schoolId, groupId, teacherMembershipId, startsAt (timestamptz), durationMin, status (default planned),
        originalStartsAt?, cancelReason?, meetingUrl?, scheduleRuleId? (onDelete: SetNull), createdAt, updatedAt
        @@unique([groupId, startsAt])  @@index([schoolId, startsAt])  @@index([teacherMembershipId, startsAt])
```

## API

Модуль `apps/api/src/modules/lessons` (правила, генерация, чтение занятий). Все эндпоинты — владелец и админ.

| Эндпоинт | Поведение |
|---|---|
| `GET /groups/:id/schedule-rules` | Действующие правила (без закрытых) |
| `PUT /groups/:id/schedule-rules` | Заменяет набор целиком. Тело: `{ rules: [{ weekday, startTime, durationMin }] }` — до 14 штук, `durationMin` 15–480, без повторов «день + время». Ответ: `{ rules, created, deleted, conflicts }` |
| `GET /groups/:id/conflicts` | Накладки преподавателя группы на горизонте |
| `GET /lessons?from&to&groupId` | Занятия за диапазон дат (в поясе школы, не больше 62 дней), по возрастанию времени. Фильтры по преподавателю и курсу добавит T-17 |

`LessonDto`: `id, groupId, groupName, course { id, name, color, icon }, teacher { id, displayName }, startsAt,
durationMin, status, originalStartsAt, cancelReason, meetingUrl` (если у занятия пусто — ссылка группы), `isOneOff`.

Сервис генерации:
- `syncGroup(groupId)` — горизонт: от сегодня до +56 дней в поясе школы; `planLessons` → `diffLessons` →
  удаление и `createMany({ skipDuplicates: true })` в одной транзакции. Архивная группа, архивный курс или
  заблокированная школа — будущие занятия по решению 3 удаляются, новые не создаются.
- `extendHorizon()` — `syncGroup` для всех неархивных групп активных школ; ошибка одной группы пишется в лог
  и не останавливает остальные. Запускается `@Cron('0 2 * * *', { timeZone: 'UTC' })`.
- Вызовы из модуля курсов: после смены преподавателя группы — будущим `planned`-занятиям по правилам проставить
  нового преподавателя; после смены дат группы, архива и возврата из архива — `syncGroup`.
- Накладки: другие `planned`-занятия того же преподавателя, пересекающиеся с занятиями группы, не больше 20:
  `{ startsAt, durationMin, otherGroupName, otherStartsAt, otherDurationMin }`.
- Сохранение правил — в `AuditLog` (entity `Group`, action `schedule_update`).

`@nestjs/schedule`: поставь версию, совместимую с Nest 11, и проверь, что она есть в реестре. `JOBS_ENABLED` — в
`env.ts`, `.env.example`, тестовом окружении (`false`).

## Тесты API

`apps/api/test/schedule.e2e-spec.ts`:

- `describeSchoolIsolation` для четырёх эндпоинтов; права ролей;
- правило «пн и чт 15:00, 60 мин» для школы в `Asia/Dushanbe` → на 8 недель создано 16 или 17 занятий (посчитай
  ожидаемое число от даты запуска теста, не константой), первое начинается в 10:00 UTC;
- та же проверка для школы в `Europe/Moscow` → 12:00 UTC;
- повторное сохранение тех же правил: `created: 0, deleted: 0`, id занятий прежние;
- смена времени: будущие занятия заменены; занятие, вручную помеченное в базе `cancelled`, осталось, и его слот
  не заполнен; занятие с `originalStartsAt` осталось;
- пустой набор правил: будущие занятия удалены, правила с прошлыми занятиями закрыты, а не удалены;
- даты группы `startsOn`/`endsOn` ограничивают генерацию;
- накладка: две группы одного преподавателя в одно время → `conflicts` не пуст, сохранение прошло;
- `extendHorizon()` вызывается напрямую: после сдвига «сегодня» (передай время параметром) появляются новые занятия,
  повторный вызов ничего не создаёт;
- архив группы удаляет будущие занятия, прошедшие остаются; смена преподавателя группы меняет его в будущих занятиях;
- валидация: 15 правил, повтор «день + время», `startTime: '25:00'`, `durationMin: 10` — 400.

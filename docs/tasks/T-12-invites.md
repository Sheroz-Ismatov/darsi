# T-12. Приглашения и вход в школу

**Цель.** Человек открывает ссылку-приглашение в Telegram и становится участником школы: владельцем, сотрудником
или родителем. Родитель без приглашения входит по коду школы. После задачи сценарий UC-1 проходит целиком.

**Требования:** FR-1 (приём ссылки владельца), FR-9 (вход по коду школы), основа для FR-10 и FR-17.

## Решения (уже приняты, не пересматривать)

1. **Приглашение принимается только в Mini App.** Ссылка `t.me/<бот>?start=inv_<токен>` открывает бота, бот даёт кнопку,
   Mini App получает параметр и вызывает API. Экрана принятия в веб-панели нет: войти в панель без роли нельзя,
   а роль появляется как раз после принятия.
2. **Токен передаётся в теле запроса**, а не в пути: `POST /invites/accept` с `{ token }`. Адреса запросов попадают в логи,
   тело — нет. (В ARCHITECTURE.md указан путь `/invites/:token/accept` — действует это решение.)
3. **Отдельный модуль `modules/invites`** с `InvitesService`. Выпуск ссылки переезжает в него из `PlatformService`;
   T-14 и T-18 будут выпускать через него ссылки сотрудников и родителей.
4. **Сроки жизни ссылок:** владелец — 72 ч (уже есть), сотрудник — 7 дней, родитель — 30 дней. Константы в
   `packages/shared/src/contracts/invites.ts`.
5. **Повторное открытие своей же использованной ссылки — успех** без изменений (человек нажал кнопку второй раз).
   Чужой использованной — ошибка.
6. **Вход по коду создаёт активного родителя сразу.** Согласие на обработку данных и анкета — задача T-31.

### `InvitesService.issue({ schoolId, membershipId, ttlHours, actorId })` → `{ url, expiresAt }`

Перенести логику из `PlatformService.issueOwnerInvite`: отозвать прежние живые токены членства, создать новый
(в базе только хэш, `hashToken`), записать `AuditLog`. `PlatformService` оставляет проверки «школа есть», «владелец ещё
не вошёл», создание заглушки владельца — и вызывает `issue`. Тесты `platform.e2e-spec.ts` должны остаться зелёными
без изменений.

### `POST /invites/accept` — любой вошедший пользователь, без `X-School-Id`

Тело: `{ token }`, строка `^[\w-]{20,64}$`. Ответ `AcceptInviteResponse`:
`{ membership: { id, schoolId, schoolName, role }, webUrl: string | null }` (`webUrl` — из `WEB_URL`, только для
owner и admin; иначе `null`).

Порядок в одной транзакции:

| Проверка | Ответ |
|---|---|
| Токена с таким хэшем нет | 404 `INVITE_NOT_FOUND` |
| Использован, и членство уже принадлежит этому же пользователю | 200, как при успехе, ничего не меняя |
| Использован или отозван, либо членство деактивировано | 409 `INVITE_USED` |
| Истёк | 410 `INVITE_EXPIRED` |
| Школа заблокирована | 403 `SCHOOL_BLOCKED` |

Затем:
1. Захватить токен: `updateMany` по `id` с условием `usedAt: null, revokedAt: null` → `usedAt = now`. Затронуто 0 строк —
   409 `INVITE_USED` (два одновременных запроса: побеждает один).
2. Найти членство этого пользователя в этой школе с той же ролью.
   - **Нет** — привязать заглушку: `userId`, `status: 'active'`.
   - **Есть** — слить: вызвать `mergeMembership(tx, заглушка → существующее)`, существующее сделать `active`,
     токены заглушки перевесить на существующее, заглушку удалить. `mergeMembership` — отдельная функция в модуле;
     сейчас она переносит только `InviteToken`, в T-18 в неё добавят перенос связей «родитель — ученик».
3. `AuditLog`: entity `Membership`, action `accept_invite`, `after: { role }`.

### `POST /schools/by-code/:code/join` — любой вошедший пользователь, без `X-School-Id`

`code` проверяется `schoolCodeSchema`. Ответ `JoinSchoolResponse`: `{ membership: {…как выше}, created: boolean }`.

| Случай | Ответ |
|---|---|
| Школы с кодом нет | 404 `SCHOOL_NOT_FOUND` |
| Школа заблокирована | 403 `SCHOOL_BLOCKED` |
| Уже активный родитель | 200, `created: false` |
| Родитель деактивирован школой | 403 `MEMBERSHIP_DEACTIVATED` |
| Иначе | 201, создать `Membership` (role `parent`, `active`, `displayName` — имя и фамилия из `User`), `created: true` |

Гонку двух одновременных запросов закрывает уникальный индекс `(school_id, user_id, role)`: поймать `P2002` и вернуть
существующее членство.

## Тесты

`apps/api/test/invites.e2e-spec.ts` (образец — `platform.e2e-spec.ts`, фикстура `createTenantFixture`):

- принятие: посторонний пользователь становится владельцем новой школы; `/me` показывает членство `active`;
- повтор тем же пользователем — 200; другим пользователем — 409 `INVITE_USED`;
- истёкшая ссылка (сдвинуть `expiresAt` в базе) — 410; отозванная (выпущена новая) — 409; неизвестная — 404;
  неверный формат — 400;
- два одновременных принятия разными пользователями (`Promise.all`) — ровно один успех;
- слияние: пользователь уже админ школы и принимает вторую ссылку админа — членство одно, заглушки нет;
- заблокированная школа — 403; без входа — 401;
- вход по коду: новое членство родителя (201), повтор — 200 `created: false`, неизвестный код — 404,
  деактивированный — 403, заблокированная школа — 403;
- ссылка владельца из `platform` принимается через `/invites/accept` (сквозной UC-1 на уровне API).
